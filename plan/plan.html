1. Overview

A procedural Python pipeline that, for each configured country and indicator, pulls World Bank API data (one request series per country+indicator), lands it as raw JSON, schema-checks it, stages it as a pipe-delimited file, runs a row_count data quality test, archives the landing files, upserts staging into a per-indicator base table with lineage columns, and finally runs a DuckDB SQL analysis (life expectancy by GDP per capita per country).

Key decisions at a glance
  • One landing file per page (<C>_<I>_<request_id>_p<page>.json), each holding that page's raw 2-element response array; all pages of a pull share one request_id and one log file (decision A1, human-approved).
  • api.per_page defaults to 3 in config, so each pull is 7 records over 3 pages and paging is visible against the live API (decision A8).
  • row_count failure (decided A2): halt the whole pipeline before archive and merge for that indicator, leave landing files in place, write a FAIL report, exit non-zero. A rerun re-pulls only the failed request_ids; a staging problem tied to landing files is handled the same way.
  • Retries (decided A7): 429, 5xx and connection errors/timeouts all use the same policy: sleep 60s, retry, fail after 3 retries.
  • Everything is read as strings (dtype=str) in merge, so business values never drift through float formatting and reruns are byte-stable.
  • Base rows store the latest request_id and staging_merge_id as scalar columns plus the two ;-joined lineage lists (ids contain neither ; nor |), appended with a no-duplicate guard.
  • Phase 5 commits everything, including generated data, logs, reports and analysis output; the plan introduces no .gitignore (section 4, A13).
  • All dates, paths, countries, indicators, primary keys and retry settings come from config/pipeline.yaml. Adding a country or indicator is a YAML-only change.
  • All I/O seams (HTTP, sleep, clock) are injectable keyword parameters at every layer, including main, so tests mock the API with no network.
  • Revision 2 (after plan review): duplicate-key and identity problems are caught inside the pull so a bad landing file can never deadlock reruns; stale/multiple landing files have a pinned recovery rule; the “latest report” rule is defined; pytest temp files stay inside the project.
  • Revision 4 (human decisions): per-page landing files, 5xx/connection retries, per_page: 3, scalar request_id/staging_merge_id in base, commit-everything, terminology cleanup (“response metadata, array element 0”). Questions Q1-Q12 are resolved into assumptions (section 17).

2. Architecture and data flow

Per indicator the steps run strictly in order. The indicator loop is sequential; within an indicator, countries are pulled one at a time (one request series per country+indicator). Analysis runs once at the end after all indicators have merged.

Design principles
  • Small restart unit. The unit of work is (country, indicator). A pull's pages live only in memory until the pull is complete and schema-checked, then are written atomically. A failure never leaves a partial landing file; a crash during the page renames can leave a partial page set, which is always detected (section 6).
  • Fail loudly. Every failure raises a specific exception with a clear message; the entrypoint maps it to a non-zero exit code. No silent drops, no swallowed exceptions.
  • Config over code. Only structural constants live in code (column names of the flattened record, lineage column names).
  • Injectable seams. http_get, sleep and now are keyword parameters with real defaults (requests.get, time.sleep, lambda: datetime.now(timezone.utc)).
  • Atomic writes. Every file is written to a temp name in the same directory and renamed with os.replace. A pull's page files are all written as temp files first and renamed only after the whole pull has passed (see section 6); staging verifies the page set is complete.

Validation rules (validate_config)

  • Required keys present; countries and indicators non-empty; no duplicates; start <= end (ints).
  • Each country matches ^[A-Z]{3}$ (ISO3). api.path_template contains {country} and {indicator}. api.per_page is null, a positive int or a digit string.
  • request_id.format must match ^%Y%m%d[^%]*%H[^%]*%M[^%]*%S[^%]*%f$ (year, month, day, hour, minute, second, microsecond in that order, only literal non-% separators), so ids are fixed-width and sort lexicographically in chronological order (the keep-newest rule depends on it). Validation renders two sample timestamps and asserts order and equal width; the rendered id must contain none of ; | / _ or whitespace (so landing file names parse unambiguously).
  • Each indicator has code, name, table_name, primary_key: a non-empty list that is a subset of the business columns (countryiso3code, date, indicator_id, indicator_name, country_id, country_name, value, unit, obs_status, decimal), so request_id/staging_merge_id are never allowed. The primary key must include countryiso3code (the column that varies across pulls). A key without it would make every multi-country staging a duplicate-key failure and cause endless re-pulls, so it is rejected with a ConfigError.
  • retry.max_retries >= 0, sleep_seconds >= 0, retry_on_5xx/retry_on_connection_errors booleans.
  • analysis.tables values must be configured indicator codes.
  • Resolved paths stay inside the project root. Violations raise ConfigError.
  • Country and indicator codes must not contain / or |. Landing file names are parsed with the regex ^(?P<C>[A-Z]{3})_(?P<I>.+)_(?P<R>[^_]+)_p(?P<N>\d+)\.json$ and then checked against the configured country and indicator (indicator codes may contain . but the request_id never contains _).
Adding a country = append to countries. Adding an indicator = append a block to indicators (own primary_key, table_name). No code change; folders are created on demand.

6. request_id and paging design

  • One request_id per pull (country+indicator). ingest_pair calls generate_request_id exactly once, before the first page request, and passes it down. All pages, all page files and the log file share it.
  • Format: UTC strftime("%Y%m%dT%H%M%S%f"), 21 characters (8 date + T + 12 time), e.g. 20261108T153045123456. Microseconds plus sequential pulls make collisions practically impossible; ingest_pair additionally refuses to proceed (raises FileCollisionError, exit 8) if the log path or any target page-file path already exists, rather than overwrite. now is a zero-arg callable returning an aware UTC datetime (default lambda: datetime.now(timezone.utc)), called once per pull.
  • Paging: request page 1 (per_page from config, default 3); read pages from that response's metadata (array element 0); request pages 2..pages. Per-page checks: metadata page equals the requested page, pages equals the first response's pages, total equals the first response's total. Any mismatch is a SchemaCheckError (a dataset drifting mid-pull means the pull restarts, the stated restart policy). With 7 records and per_page=3 the live API gives pages=3 (3+3+1 records); the per-page record count is not asserted, only the total (by row_count).
  • Primary-key uniqueness across pages: after all pages are fetched, fetch_pull flattens the records, and if any configured-PK value repeats (the unordered API can repeat a row on one page and drop another while the count still equals total) it raises SchemaCheckError. Nothing is written, so the pull is simply restarted on the next run and a bad landing set can never exist.
  • pages == 0 or total == 0 (empty pull) fails (A6).
  • Recording total and pages: total and pages are taken from the response metadata of the first page request (after its schema check) and held in memory. The log file is written once the whole pull has succeeded, immediately before the page files, so a failed pull leaves no log (A4).
  • One landing file per page. Landing files are named <C>_<I>_<request_id>_p<page>.json in storage/landing/<I>/; each holds that page's raw, unmodified 2-element response array [metadata, records]. The prompt's name has no page number; the page suffix is a human-approved deviation (A1) that keeps one file = one raw API response.
Write order, atomic page set and crash windows

Order after a fully successful pull: (1) log written atomically; (2) every page file written to <name>.part; (3) all .part files renamed to their final names with os.replace (pages in order 1..N).

  • Crash during (1) or (2): no final landing file exists; at most an orphan log (harmless: row_count walks landing files, not logs) and *.part files, which are never listed as landing and are deleted at the start of the next ingest.
  • Crash during (3): a partial set of final files exists. A partial set is never mistaken for a complete pull because every consumer verifies completeness: check_page_set requires page numbers exactly 1..pages (pages from response metadata, identical in all files, each file's metadata page equal to the number in its name). ingest_indicator treats an incomplete newest group as invalid (moved to rejected/, pair re-pulled); staging raises StagingError naming that request_id (marked for re-pull, section 9). The log is checked by row_count only for complete sets.
  • A request_id's page files are always moved (archive or rejected) together by move_request_files.

7. Schema check spec

schema_check(page_response, cfg, country, indicator_code, expected_page) is called on every page immediately after it is parsed and before anything is written. Both elements of every page's response array are checked: element 0 (the response metadata: page, pages, per_page, total, sourceid, lastupdated) and element 1 (the list of records, with every record's shape and types). It collects all violations, then raises SchemaCheckError whose message names country, indicator, page and every error. The pull stops; nothing is written for it; no rows are dropped or coerced. Staging re-runs the same function on every landing page file against the current config.

8. Request log format

  • Path: log/<indicator-code>/<request_id>.log, one file per request_id (per pull, not per page file).
  • Content: exactly one line, pipe-delimited, terminated by \n, no header: 
    request_id|total|pages|country_code|indicator_code

  • total and pages come from the response metadata (array element 0) of the first page request; with the default per_page=3 a pull of 7 records logs pages=3. country_code is the ISO3 code from config (the requested country).
  • Reader dq_tests.read_request_log splits on |, requires exactly 5 fields, ints for 2 and 3, and that field 1 equals the file stem.
  • Separate operational run log: Python logging to stderr and log/pipeline.log, format %(asctime)s %(levelname)s %(message)s. This is not the request log and has no tests tied to its format.

9. row_count test spec and report format

Algorithm (row_count_test)

  1. Input: frames from build_country_frames: one entry per request_id whose DataFrame is the concatenation of all that request_id's page files (the per-country frame), captured before combine_frames.
  2. For each request_id: read its log, expected_total = total; actual_rows = len(frame) (all records across all pages, including null-valued rows).
  3. status = PASS if equal else FAIL. A missing/malformed log, or a country in the log that differs from the landing file names, is FAIL with an explanatory detail (never an unhandled exception).
  4. Write the report even when failing, then assert_row_count_passed raises RowCountFailure if any FAIL.

Report

Path: tests/<indicator-code>/row_count/row_count_<checked_at_ts>_<staging_merge_id>.psv where checked_at_ts is UTC %Y%m%dT%H%M%S%f. One file per test run, one row per request_id, pipe-delimited, with header (one-report-per-run layout is an accepted interpretation of “a pass/fail report per request_id”, A12):

request_id|country_code|indicator_code|expected_total|actual_rows|status|detail|staging_merge_id|checked_at
20261108T153045123456|BRA|SP.POP.TOTL|7|7|PASS||c0a8...|2026-11-08T15:31:02Z
20261108T153047001122|CAN|SP.POP.TOTL|7|6|FAIL|log total 7 != dataframe rows 6|c0a8...|2026-11-08T15:31:02Z

Failure behavior (decision A2)

  • Any FAIL for an indicator: halt the whole pipeline (non-zero exit 5) before archive and merge of that indicator. Landing files and the staging file stay in place; the base table is untouched.
  • Indicators already fully merged earlier in the same run stay merged (their merge is idempotent and valid). Later indicators are not started. Analysis does not run.
  • “Latest report” rule (B3): among files matching row_count_*.psv, the one whose filename is lexicographically greatest, which equals the most recent checked_at_ts. Ties are impossible (microsecond timestamp + uuid) but mtime would be the documented tiebreak.
  • Rerun: ingest_indicator reads the latest report; for FAIL request_ids it re-pulls only that country (new request_id), moves the superseded request_id's page files together to storage/rejected/<ind>/, and keeps PASS landing sets as they are. Staging is rebuilt (new staging_merge_id) and the test reruns.
  • Staging failures are treated like FAILs (B1, N2): every staging-time problem tied to landing files is a StagingError carrying .request_ids (duplicate PK, leftover file failing the current-config schema re-check, unreadable/mismatched file, incomplete or inconsistent page set). run_indicator writes those ids to the marker file (paths.staging_failed_marker, spec under failed_request_ids, section 5); failed_request_ids returns them, so the next run re-pulls just those pairs and clears the marks when the old files move to rejected/. No deadlock. Duplicate PK that spans different request_ids is only possible with a bad primary key, which config validation rejects (N6).

10. Staging and staging_merge_id

  1. build_country_frames lists landing/<I>/*.json grouped by request_id, verifies each group's page set is complete and consistent (check_page_set), re-runs schema_check (both array elements) on each page against the current config (stale files from a removed country or different date range fail with request_id attached), and concatenates a request_id's pages (flatten_records) into one per-country frame, all columns as strings using the pinned conversion (None to empty, int to str, float to repr). At most one request_id per (country, indicator) is allowed; otherwise StagingError (ingest recovery guarantees this).
  2. Frames are kept in the dict keyed by request_id for the row_count test.
  3. combine_frames concatenates, sorts by PK, and asserts PK uniqueness (a duplicate would mean the unordered API paging produced a repeat; fail loudly). It only stacks the per-country frames into the staging table; it does no upsert. The upsert is merge_frames (section 12). A pipe/newline in any field makes write_psv raise ValueError, which build_staging re-raises as StagingError.
  4. new_staging_merge_id() = uuid4, generated when the staging table is created, added as column staging_merge_id (same value on every row).
  5. Output file: storage/staging/<I>/<I>_staging.psv, a stable name overwritten each run (staging is a transient table; decision A9). Columns: countryiso3code|date|indicator_id|indicator_name|country_id|country_name|value|unit|obs_status|decimal|request_id|staging_merge_id.

Order in the run: stage, then row_count test, then archive. The staging file is written before the test (spec step 2 then 3) and is not deleted on failure.

11. Archive step

  • Only called after assert_row_count_passed succeeds.
  • archive_landing calls move_request_files for each request_id: all page files of that request_id are moved together (shutil.move, effectively a rename on the same filesystem) to storage/archived/<I>/. All targets are checked first; names embed request_id and page, so there are no collisions, and a pre-existing target raises FileCollisionError (exit 8) with nothing moved.
  • Postcondition: landing directory for the indicator contains no files (asserted).
  • Crash window archive to merge (R2): the staging file survives while landing is empty. At the start of run_indicator, merge_leftover_staging checks: landing empty, staging file present, its staging_merge_id not found in the base staging_merged_id_linage column (or base missing), a row_count report for that staging_merge_id exists with every row PASS, and for every request_id in the staging file the complete page set p1..p{pages} is in archived/ → merge it first. This guard (also on the base-missing branch) guarantees staging that failed row_count, or whose archive never finished, is never merged. Then the run proceeds normally with fresh pulls. If the staging id is already in the lineage nothing happens, and if it were merged twice the lineage guard (12) makes it a no-op. A leftover staging file is never merged while landing files exist (the run is about to overwrite it).

12. Merge / upsert design

Inputs and typing

Staging and base are both read with read_psv (dtype=str, keep_default_na=False). All business values are compared and written as the same strings the staging file contains, so no float round-trip or dtype inference can alter them (e.g. 2185821610689.31 stays textual; date keeps leading format). Staging values were produced once from the JSON by the pinned per-record conversion in section 5 (None to empty, int via str, float via repr, strings unchanged); repr(float) is shortest-round-trip. Merge never re-converts them.

Columns

Base columns (14, in this order):

  • Business columns (10): countryiso3code, date, indicator_id, indicator_name, country_id, country_name, value, unit, obs_status, decimal.
  • Latest-id scalars (2), decision A19: request_id and staging_merge_id, always the latest value for that row: overwritten on every update and set on every insert.
  • Lineage lists (2): request_id_linage and staging_merged_id_linage (history, appended). (Note the intentionally different spellings: staging_merge_id scalar, staging_merged_id_linage list, as specified.)

Only the 10 business columns can be primary-key columns. On an identical rerun the business values stay identical, while request_id, staging_merge_id and both lineage lists change.

Algorithm (merge_frames)

  1. If base is missing (storage/data/<I>/<I>.psv absent): first run = every staging row is inserted with scalar request_id/staging_merge_id copied from staging, request_id_linage = request_id and staging_merged_id_linage = staging_merge_id.
  2. Else index both frames by the configured PK (composite). Assert base PK unique (MergeError) and base business columns match staging (MergeError on schema drift).
  3. Existing key (in both): overwrite all business columns from staging (update); overwrite the scalars request_id and staging_merge_id with the staging row's values; request_id_linage = append_lineage(old, row.request_id); staging_merged_id_linage = append_lineage(old, row.staging_merge_id).
  4. New key (staging only): insert with the scalars from staging and single-element lineage lists.
  5. Key only in base: kept untouched: values, scalars and lineage unchanged (no delete; decision A5).
  6. Sort by PK, write with write_psv atomically (temp file + os.replace) to the same path, overwriting.

Serialization choice: ;-joined string

OptionForAgainst
Chosen: id1;id2;id3No quote characters, so the psv needs no CSV quoting; human-readable; trivial append; DuckDB can string_split(col, ';'). Request ids ([0-9T]) and UUIDs ([0-9a-f-]) never contain ; or |; append_lineage asserts this.Not self-describing as a list; breaks if future ids contain ; (assertion catches it).

Dedupe

  • append_lineage appends new_id only when it is not already in the list. Within one real run each id is new, so each rerun grows each list by exactly one per row touched; replaying the same merge (same staging file) appends nothing.
  • PK duplicates are rejected earlier (staging) and in base (merge).

Idempotency proof sketch

  1. Let B be base and S staging. Business part of merge(B,S) is a function of S on keys of S and of B elsewhere: biz(M)[k] = S[k] for k in S, else B[k].
  2. Applying it again with the same S gives biz(M2)[k] = S[k] for k in S, else M[k] = B[k]: identical to biz(M). So business data is a fixed point (strings are never reinterpreted, and sorting is deterministic, so the business bytes are identical). The same argument applies to the latest-id scalars: ids(M)[k] = ids(S)[k] for k in S, else unchanged, so they are a fixed point under replay of the same S too.
  3. A rerun that pulls identical data produces a new S' with biz(S') = biz(S) but fresh ids. The 10 business columns are therefore unchanged; the scalar request_id/staging_merge_id of every touched row are overwritten with the new ids; each touched row's two lineage lists grow by exactly one element. So only the 4 metadata columns (scalars + lineage) differ, as required.
  4. Replay of the identical S (crash after merge, rerun of merge): the scalars are overwritten with the same values and the ids are already lineage members, append_lineage is a no-op, so the output file is byte-identical.
  5. Atomic overwrite means a crash leaves either the old or new complete base.

Why not DataFrame.merge naive or DuckDB?

Plain pandas on string frames keeps the logic small, testable and independent of DuckDB; DataFrame.set_index(pk) + combine/concat + explicit loop for lineage is acceptable at this size (252 rows total). Implementation choice is left to the Coding agent as long as the contract above holds.

13. DuckDB analysis SQL design

analysis.load_base_tables(con, cfg) creates for each indicator: CREATE OR REPLACE TABLE <table_name> AS SELECT * FROM read_csv('<path>', delim='|', header=true, all_varchar=true). It also creates views named by analysis.tables (life_expectancy, gdp_per_capita) over those tables, so the SQL file is static and stands alone. The base files have 14 columns (including the scalar request_id and staging_merge_id); the loader keeps them all and the SQL selects only countryiso3code, date and value by name, never SELECT *, so extra columns do not affect the analysis. DuckDB version (decision A16): the Coding agent verifies the installed DuckDB supports named parameters in con.execute; if not, it falls back to substituting the two validated integers (int()-checked config values) into the SQL text. The Python side binds $start_year and $end_year from config (con.execute(sql, {"start_year": 2018, "end_year": 2024})) and writes the result with pandas to_csv(sep="|", index=False).

Metrics and why

  • n_years: number of country-years with both values; guards the interpretation (max 7).
  • avg_life_expectancy and avg_gdp_per_capita: simple level summaries for each country over the window.
  • corr_le_gdp_pc: Pearson correlation between yearly life expectancy and yearly GDP per capita within the country, the direct "life expectancy by GDP per capita" relationship. NULL (empty cell) when a series is constant or n<2.
  • slope_years_per_10k_usd: REGR_SLOPE(le, gdp_pc) * 10000, the effect size (years of life expectancy per US$10,000), because correlation alone hides magnitude.

Caveats to state in README: n≤7 per country, shared time trends and the 2020-2021 COVID dip confound the relationship, correlation is not causation.

Draft sql/code/analysis.sql

-- Life expectancy by GDP per capita, per country, for the configured date range.
-- Tables/views expected: life_expectancy, gdp_per_capita
--   (columns: countryiso3code, date, value, ... all VARCHAR, as loaded from the base .psv files)
-- Parameters: $start_year, $end_year (bound by src/analysis.py from config/pipeline.yaml)
WITH joined AS (
    SELECT
        le.countryiso3code,
        CAST(le.date AS INTEGER)           AS year,
        TRY_CAST(le.value AS DOUBLE)       AS life_expectancy,
        TRY_CAST(g.value  AS DOUBLE)       AS gdp_per_capita
    FROM life_expectancy AS le
    INNER JOIN gdp_per_capita AS g
        ON  le.countryiso3code = g.countryiso3code
        AND le.date            = g.date
    WHERE CAST(le.date AS INTEGER) BETWEEN $start_year AND $end_year
),
complete AS (
    SELECT * FROM joined
    WHERE life_expectancy IS NOT NULL AND gdp_per_capita IS NOT NULL
)
SELECT
    countryiso3code,
    COUNT(*)                                              AS n_years,
    MIN(year)                                             AS first_year,
    MAX(year)                                             AS last_year,
    ROUND(AVG(life_expectancy), 2)                        AS avg_life_expectancy,
    ROUND(AVG(gdp_per_capita), 2)                         AS avg_gdp_per_capita,
    -- CORR on a constant series can yield NaN; normalize NaN to NULL
    CASE WHEN isnan(CORR(life_expectancy, gdp_per_capita)) THEN NULL
         ELSE ROUND(CORR(life_expectancy, gdp_per_capita), 4) END   AS corr_le_gdp_pc,
    CASE WHEN isnan(REGR_SLOPE(life_expectancy, gdp_per_capita)) THEN NULL
         ELSE ROUND(REGR_SLOPE(life_expectancy, gdp_per_capita) * 10000, 4) END
                                                          AS slope_years_per_10k_usd
FROM complete
GROUP BY countryiso3code
ORDER BY countryiso3code;

Tests must pin the constant-series behavior: the output cell is empty (NULL), never the text nan. (If isnan is applied to a NULL, e.g. n=1, the CASE yields NULL via the ELSE branch's NULL input, also empty.) If the installed DuckDB returns NULL already, the CASE is harmless.

Output: sql/analysis/life_expectancy_by_gdp_per_capita.psv with those 8 columns, 9 rows (one per country). A countries-with-no-data case simply yields no row (flagged in the run log if rows != number of countries).

   [--indicator SP.POP.TOTL ...]   # subset (default: all in config order); also the resume path after a later-indicator failure
   [--skip-analysis]

   [--log-level INFO]

  2. For each indicator in config order: merge_leftover_staging (guarded, section 11), then ingest_indicator (steps: request_id, fetch pages, schema check each page, PK uniqueness, log, page files) -> build_staging -> row_count_test + write_row_count_report + assert_row_count_passed -> archive_landing -> merge_indicator.
  3. After all indicators succeed: run_analysis.
  4. Exit 0, or the mapped code (section 5) on the first PipelineError.
